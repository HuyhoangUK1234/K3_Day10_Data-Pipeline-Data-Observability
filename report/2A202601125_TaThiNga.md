## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết
Hệ thống Pipeline rất dễ sinh ra rác ("Garbage In, Garbage Out"). Phần việc của mình giải quyết 2 bài toán:
1. "Chốt chặn": Tự động phát hiện dữ liệu lỗi (trống, trùng lặp) và dừng pipeline (Fail) trước khi nó đi vào hệ thống RAG.
2. "Báo cáo": Đưa ra bức tranh tổng thể về hiệu năng RAG (Metrics) và chất lượng (Quality) dưới định dạng Markdown dễ đọc cho người kiểm duyệt thay vì phải đọc file log.

### Cách triển khai
- **Quality**: Mình chia các luật ràng buộc dữ liệu (checks) làm 2 nhóm: `critical` (bắt buộc đạt) và `warning` (chỉ cảnh báo). Ví dụ: title rỗng là critical, độ cũ dữ liệu là warning. Nếu không có lỗi critical, pipeline được đánh giá là PASS.
- **Reporting**: Viết hàm để render (hiển thị) Markdown sử dụng f-string, tự động tính `delta` (sự chênh lệch) giữa Corrupted và Baseline để hiện mũi tên tăng/giảm (+ / v).

### Input, output và contract

| Thành phần                   | Mô tả                                     |
| ------------------------------ | ------------------------------------------- |
| Input                          | Pandas DataFrame đã qua Cleaning (`papers_clean.json`) |
| Output                         | JSON logs chứa trạng thái Pass/Fail và Markdown tables |
| Module phụ thuộc             | `src/ingestion/cleaning.py` (cung cấp data) |
| Module sử dụng output        | `src/pipelines/phase1.py` & `corruption_flow.py` |
| Điều kiện lỗi cần xử lý | Empty dataframe, cột dữ liệu bị thiếu trong lúc corrupt |

### Cách xác minh

```bash
python script/run_corruption_flow.py
```
- **Kết quả mong đợi:** Script hoàn thành không crash. Log báo Corrupted Fail, Repaired Pass.
- **Kết quả thực tế:** Script đã ghi đè thành công báo cáo. Metrics RAG thể hiện đúng sự suy giảm và phục hồi.
- **Artifact/log:** `data/reports/corruption_report.md`

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Xử lý tiêu chí Freshness (Độ tươi/mới) của bài báo.
- **Các phương án đã cân nhắc:** (1) Báo lỗi Critical và ngừng pipeline nếu quá 180 ngày; (2) Chỉ ghi log Warning và cho pipeline đi tiếp.
- **Phương án đã chọn:** Phương án (2) - Chỉ báo Warning.
- **Lý do:** Freshness là rủi ro nghiệp vụ (upstream API chậm), không phải lỗi cấu trúc (schema error) làm hỏng code. Chặn toàn bộ data chỉ vì một dòng dữ liệu hơi cũ là đánh đổi không hợp lý về mặt độ sẵn sàng hệ thống (availability).
- **Bằng chứng quyết định phù hợp:** Trong Baseline report, dù test freshness báo WARN, hệ thống vẫn PASS và RAG vẫn hoạt động tốt (đạt điểm F1 = 1.0).

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:** Băn khoăn không biết liệu chạy pipeline báo 10/11 có phải là lỗi hệ thống (Bug) cần sửa bằng mọi giá không.
- **Lệnh hoặc bước tái hiện:** Chạy `python script/run_phase1.py` và kiểm tra file `phase1_report.md`.
- **Nguyên nhân gốc:** Không hiểu rõ sự khác biệt giữa Data Integrity (Critical) và SLA Monitoring (Warning).
- **Cách xử lý:** Đọc lại logic code của `quality.py`, nhận ra thiết lập `severity="warning"` là chủ đích thiết kế. Giữ nguyên ngưỡng 180 ngày thay vì cố sửa để lấy 11/11.
- **Cách xác minh sau khi sửa:** Report vẫn thể hiện 10/11 và overall là PASS.
- **Điều học được:** Lỗi (Fail) trong data pipeline không phải lúc nào cũng xấu, nó chính là bằng chứng cho thấy hệ thống Data Observability đang làm tốt nhiệm vụ cảnh báo rủi ro.

## 7. Hiểu biết về luồng end-to-end

1. **Dữ liệu đi từ Crossref đến vector index như thế nào?**
   Gọi API Crossref -> Lấy JSON thô -> Dọn dẹp/Clean bằng Pandas -> Nối text các trường cần thiết thành `text_for_embedding` -> Đưa qua `sentence-transformers` -> Lưu vector embedding và metadata vào `ChromaDB`.
2. **Evaluation set và ground-truth document IDs dùng để đo retrieval/answer quality ra sao?**
   Đánh giá xem agent lấy (retrieve) tài liệu có chứa đúng `ground_truth_doc_ids` hay không (đo Hit rate). Lấy `answer` do agent sinh ra so sánh với `ground_truth` (bằng Token F1 và mô hình LLM-as-a-judge).
3. **Quality checks khác freshness monitoring ở điểm nào trong bài lab?**
   Quality checks giám sát định dạng, tính đầy đủ (null/unique). Freshness giám sát độ trễ (latency/age) so với mốc hiện tại.
4. **Vì sao phải dùng cùng test set cho baseline, corrupted và repaired?**
   Để đảm bảo biến số duy nhất thay đổi là "chất lượng dữ liệu". Nếu đổi bộ câu hỏi khác, ta sẽ không biết agent trả lời tệ hơn là do câu hỏi khó hay do dữ liệu bẩn.
5. **Repair được xem là thành công dựa trên artifact và metric nào?**
   Artifact `repaired_quality.json` phải báo `success: true`. Các metrics như Hit rate, F1 phải phục hồi về ngang (hoặc gần sát) mức Baseline trong `repaired_metrics.json`.

## 8. Phân tích kết quả

### Metrics chính

| Metric/signal          | Baseline | Corrupted | Repaired | Nhận xét của cá nhân |
| ---------------------- | -------: | --------: | -------: | ------------------------- |
| `retrieval_hit_rate` |     1.00 |      0.80 |     1.00 | Tụt giảm mạnh (20%) khi corrupt, lấy lại hoàn toàn 100% khi repair. |
| `mean_token_f1`      |     1.00 |    0.7593 |     1.00 | Agent trả lời sai/thiếu ý hẳn khi data bị bẩn. |
| `judge_accuracy`     |     1.00 |      0.75 |     1.00 | Judge cũng đánh giá agent dở hơn trong tập Corrupted. |
| `mean_judge_score`   |     5.00 |      4.00 |     5.00 | Thang điểm 5/5 giảm xuống 4/5. |
| Quality checks         |    10/11 |      6/11 |    10/11 | Phát hiện chuẩn xác việc dữ liệu bị hỏng (id trùng, null...). |
| Freshness status       | STALE(1) |  STALE(4) | STALE(1) | Bị corrupt làm cũ ngày dẫn đến 4 rows bị stale, sau repair về lại 1 row như gốc. |

### Kết luận từ số liệu

1. Data corruption (Xóa summary, trùng id, lùi ngày) → quality/freshness signal báo FAIL đỏ chót → agent metric suy giảm nghiêm trọng (Hit Rate giảm từ 100% còn 80%, F1 giảm).
2. Repair action (Chạy lại từ raw json) → quality/freshness signal phục hồi về PASS → agent metric phục hồi lại mức 100% nguyên bản.

Corruption ảnh hưởng rõ nhất là **làm trống `summary`**. RAG phụ thuộc vào content để trả lời, nếu text bị rỗng thì vector sinh ra sai hoặc vô nghĩa, dẫn đến lúc truy vấn không tìm được (Hit rate tụt), kéo theo việc không có thông tin để trả lời (F1 tụt).

## 9. Điều học được và hướng cải thiện

### Ba điều quan trọng nhất

1. **Hiểu được triết lý "Garbage In, Garbage Out"**: AI xịn đến mấy mà cung cấp cho nó một file JSON/CSV thiếu nội dung thì nó cũng sẽ trả lời ngớ ngẩn (như minh chứng từ điểm F1 bị tụt).
2. **Kỹ năng chia mức độ lỗi**: Học được cách không phải bất cứ thứ gì không hoàn hảo (vd: dữ liệu cũ) cũng phải đập bỏ. Việc phân loại Critical và Warning giúp pipeline linh hoạt hơn.
3. **Giá trị của Data Observability**: Nếu không có các hàm trong file `quality.py` và báo cáo `reporting.py` của mình, khi hệ thống RAG trả lời sai, người ta sẽ đổ lỗi cho Model dở. Có Data Observability, ta biết ngay lỗi nằm ở khâu dữ liệu.
